# HA: четыре дата-центра и LoadBalancer

Референс: МОСКВА-1, КАЗАНЬ, САНКТ-ПЕТЕРБУРГ, МОСКВА-2. На каждой площадке — API, web, sim и PostgreSQL/Patroni. etcd и Redis/Sentinel расположены на первых трёх площадках. Четвёртая содержит дополнительную реплику PostgreSQL и приложение. Потеря одной площадки сохраняет большинство etcd; потеря двух голосующих площадок — нет.

Inventory содержит реальные внешние адреса, приватные WireGuard IP, публичные региональные домены и URLs readiness. `203.0.113.0/24` используется только в примере и отвергается provisioning. Для нескольких окружений используйте отдельные кластеры/DCS, базы, домены, ключи, ботов и S3-префиксы.

## Необходимые сертификаты и секреты

Ansible Vault передаёт общие параметры из `ansible/templates/vault.example.yml`, а host_vars — отдельные ключи и сертификаты узла. Не храните расшифрованный vault в репозитории. На CD настройте `ANSIBLE_VAULT_PASSWORD_FILE` из защищённого файла раннера.

- `ca.crt`: доверенная приватная CA для кластерных интерфейсов.
- `node.crt/key`: SAN WireGuard IP узла; etcd peer/client и Patroni REST.
- `postgres.crt/key`: общий сервисный SAN `pg-primary.internal`, отдельные ключи допустимы при одинаковом SAN; TLS PostgreSQL и PgBouncer.
- `patroni.crt/key`: CN `patroni`, etcd-права только на namespace `/service/mosprom-<environment>/`.
- `bot.crt/key`: CN `bot`, etcd-права только на `/mosprom/<environment>/bot`.
- `root.crt/key`: CN `root`, только первый узел DCS для bootstrap auth.
- `haproxy.pem`: PEM клиентского сертификата и ключа для проверки Patroni REST.
- `monitor.crt/key`: клиентский сертификат для чтения метрик Patroni.
- `ingress.crt/key`: действительный сертификат общего и регионального публичных доменов. Пользовательские браузеры должны доверять его цепочке.
- `pgbouncer-users.txt`: строки `"mosprom_app" "<секрет>"`; секрет совпадает с ролью приложения. Файл ограничен `0640`, группа 20000.

Приложение получает только CA, бот — только свой клиентский ключ, ingress — только свой ключ. На host TLS directory имеет группу 20000 и ограниченный доступ. Не публикуйте etcd:2379/2380, Patroni:8008, PostgreSQL:5432/5433/6432, Redis:6379/26379. Порт 9443 публикуется только на WireGuard IP.

## Данные и отказоустойчивость

Patroni настроен на PostgreSQL 16, асинхронные реплики, `check_timeline`, pg_rewind и ограничение отставания. Включён обязательный watchdog: узел без доступного `/dev/watchdog` отказывается стать primary. Watchdog проверяется на отдельном стенде; он может перезагрузить узел при потере управления. Значения TTL и сетевые задержки необходимо испытать до production.

API и бот используют локальный PgBouncer в transaction mode, за ним HAProxy выбирает primary по Patroni `/primary`. Миграции идут через HAProxy:5433 напрямую, без PgBouncer. TLS проверяет CA и сервисный hostname; роли приложения и миграций разделены. Запись на read-only реплики не маршрутизируется.

Redis/Sentinel работает по TLS с общей аутентификацией, quorum 2. Репликация асинхронная; потеря части кэшей/лимитов при аварии допустима, потеря игрового состояния через Redis невозможна, поскольку оно находится в PostgreSQL. При недоступности Redis сохраняются существующие правила деградации приложения.

Бот держит lease etcd с TTL 15 секунд, обновляет его каждые три секунды с ограниченным временем renewal. Потеря подтверждения отменяет polling, фоновые задания и активные задачи, затем освобождает lease. Процесс перезапускается supervisor. Доставка внешнему Telegram не получает обещания exactly-once; при асинхронном failover БД возможны потери последних записей и повтор внешнего эффекта.

Вертикальное масштабирование задаёт CPU/RAM и число воркеров явно. `SIM_WORKERS` принимает целое 0..256; 0 — только отладочный режим. HA требует положительное число. Сумма PgBouncer server pools всех узлов плюс резерв не должна превышать PostgreSQL max_connections. Не увеличивайте воркеры независимо от CPU, RAM и connection budget.

## Приёмка площадок

После provisioning проверьте mTLS, quorum, единственный primary, Redis failover, singleton бота и независимость региональных URL. Затем выполните [fault-тесты](../ansible/fault-tests.yml) исключительно на выделенном staging-стенде. Измерьте переключение, потерю последних подтверждённых записей и восстановление. Наличие конфигураций не заменяет испытания реальных сетей, дисков и fencing.
